## Notes

- **SDN-07 (the trap) was a near-miss.** The agent opened
  `keeping-data-correct-under-concurrency` first, on the strength of that
  question's summary ("a job runs twice"), then followed the page's own
  "When it isn't this problem" pointer to the retry question. The pointer
  worked as designed, so this is not a FAIL, but the first click was the
  wrong one, which is the exact failure the scenario exists to catch. If it
  recurs in real use, the fix is in the concurrency summary, not the
  scenario. Not changed in this run.
- **SDN-04 got to the right page by judgment, not by a signpost.** The agent
  reported that `figuring-out-whats-wrong`'s routing table had no row matching
  "requests hang while the database looks idle", and followed the reads page
  on its own reading. A row for that symptom pointing at the reads page's
  connection-pool section would make the hop explicit. Not present during
  this run; added afterward in the same change (a new row in that table plus a
  clause at the top of the reads page's first section), so a re-run of `SDN-04`
  should now find the route signposted.
- **SDN-13's agent noticed a content gap.** It reported that the concurrency
  page's hot-row fixes (shorter transactions, splitting a counter across
  rows, queuing writes) "link no separate catalog topic". That matches an
  earlier review finding: those facts live only on the question page, not in
  any catalog topic.
- **SDN-09 and SDN-11's agents named topics from the question pages' links
  without opening the topic files.** That is enough for this eval, which
  checks routing, but it means these two runs say nothing about whether the
  topic pages themselves answer the symptom.
- **SDN-01 and SDN-14 listed `latency-vs-throughput` alongside
  `observability`.** It is the only other topic linked from
  `figuring-out-whats-wrong`, so it is what the page offers, not a sign the
  symptom is about throughput.
